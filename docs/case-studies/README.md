# 엔지니어링 사례

라이브 봇을 운영하며 실제로 마주친 문제 다섯 가지입니다. 각 사례는 **문제 → 결정 → 검증 → 결과** 순서로 적었습니다.
사례 4~5는 원문 결정문(ADR)을 함께 실었습니다.

공통된 태도는 세 가지입니다.

1. **답을 바꾸는 최적화는 범위 밖이다.** 성능 개선은 "기존 구현과 정확히 같은가"를 대조한 뒤에만 들어갑니다.
2. **거래소가 정본이다.** 로컬 캐시가 거래소와 갈리면 캐시를 손으로 고치지 않고, 거래소에 묻거나 사람에게 넘깁니다.
3. **자료가 부족하면 위험을 여는 대신 보류한다.** 불완전한 조회는 통과가 아닙니다.

## 1. 총액 상한 경합 — 처리 순서를 계약으로 고정

| | |
|---|---|
| **문제** | 한 봉에 여러 종목이 동시에 신호를 냅니다. 총액(gross) 상한이 있으면 먼저 처리된 종목이 상한을 채우고 뒤쪽은 탈락합니다. 순회 순서가 dict 삽입 순서(= 데이터 도착 순서)에 묶여 있어, 같은 신호 집합에서도 실행마다 다른 포지션이 나올 수 있었습니다. |
| **결정** | 순서를 *성과*가 아니라 *자유도* 기준으로 골랐습니다. 신호 세기순 정렬은 성과 지표를 올리지만 신호와 상관된 선택이라 검정되지 않은 새 자유도입니다. 그래서 중립적인 알파벳순으로 고정하고, 스펙에 `mr_candidate_order_is_alphabetical: true` 로 계약을 남겼습니다. 탈락한 종목은 사유와 함께 기록해 조용히 버리지 않습니다. |
| **검증** | 5종목 120개 순열 전부가 같은 진입 목록을 내는지 확인하고, 대조군(정렬 제거)은 결과가 갈리는 것까지 확인합니다. |
| **배운 점** | 백테스트와 라이브가 다른 이유 중 상당수는 전략이 아니라 순회 순서 같은 *숨은 입력*에서 나옵니다. |

## 2. 증분 정규화 — 579 ms 를 없애되 답은 그대로

| | |
|---|---|
| **문제** | 주기마다 21개 계열 × 18k 봉을 다시 정렬하느라 579 ms 를 썼고, 다섯 슬리브가 한 스레드를 공유해 그동안 다른 슬리브 타이머가 3.2 초 밀렸습니다(head-of-line blocking). |
| **결정** | 삽입 시점에 마감 시각으로 정규화하고, 같은 마감에 원시 시각이 둘이면 *늦은 원시 시각이 이긴다*는 동률 규칙을 코드에 명시했습니다. 도착 순서가 아니라 시각이 승자를 정합니다. |
| **검증** | 결손 봉 · 같은 마감의 두 번째 시각 · 뒤섞인 도착을 섞은 200회 무작위 시험에서 증분 결과가 "전부 모아서 정렬한" 기준 구현과 근사가 아니라 정확히 같습니다. 시드를 고정해 실패하면 같은 입력으로 재현됩니다. |
| **배운 점** | 빠른 구현에는 반드시 느리지만 자명한 기준 구현을 짝으로 둡니다. |

## 3. 소유 스레드 GC — 정리가 도는 스레드를 고정

| | |
|---|---|
| **문제** | NautilusTrader 의 로거 객체는 만든 스레드에서만 해제할 수 있습니다(pyo3 `unsendable`). 그런데 파이썬의 자동 순환 GC 는 할당 문턱을 넘긴 *아무 스레드*에서 돕니다. 할당이 가장 많은 워커 스레드에서 회수가 일어나 객체를 유실하고 트레이스백이 났습니다. |
| **결정** | 자동 GC 를 끄고, 소유 스레드 하나가 60 s 주기로 회수합니다. 다른 스레드의 회수는 거부합니다. 소유 스레드는 무장 시점이 아니라 *첫 회수 시점*에 정합니다 — "무장하는 스레드 = 회수하는 스레드"는 가정이었고, 틀리면 자동 GC 를 끈 채 아무도 회수하지 않는 상태가 되기 때문입니다. |
| **검증** | 워커 스레드가 문턱을 수십 번 넘는 할당을 해도 종료자가 워커에서 돌지 않고, 소유 스레드의 회수에서만 돌며, 침입자 스레드의 회수는 거부되는지 확인합니다. |
| **배운 점** | 부하에 따라 달라지는 비결정성은 재현이 어렵기 때문에, 발생 조건을 없애는 구조 변경이 재시도나 예외 처리보다 낫습니다. |

## 4. 갇힌 취소 — 거래소에 직접 묻고 닫는다 · [ADR 0282](../adr/0282-stuck-pending-cancel-resolved-at-venue.md)

| | |
|---|---|
| **문제** | 캘린더 사다리의 취소 요청이 TLS 끊김으로 모호하게 실패했습니다. 주문은 거래소에서 `PARTIALLY_FILLED` 로 살아 있는데 로컬은 `PendingCancel` 에 머물렀고, 프레임워크는 이 상태의 재취소를 버립니다. 결국 주문이 낡은 가격에 13분 걸려 있었고, 미헤지 노출이 1,453.6 s 이어졌습니다. |
| **결정** | 60 s 마다 `PendingCancel` 로 180 s 넘게 변화 없는 주문을 하나씩 골라 거래소에 정본 상태를 묻습니다. 열려 있으면 액터가 "아직 갇혀 있다"를 승인한 경우에만 직접 취소하고 ACK 를 확인합니다. 이미 종결이면 봇이 캐시를 고치지 않고 ERROR 로 사람에게 넘깁니다. 같은 주문은 300 s 안에 다시 묻지 않고, 3회 뒤 손을 뗍니다. |
| **검증** | 시험 12건(변이 넷), 골든 재기록. 프레임워크 상류 코드(Rust)의 재조정 경로를 읽고 기존 대안(슬리브 재취소)이 왜 효과가 없는지 근거를 남겼습니다. |
| **결과** | 갇힌 취소가 3~8분 안에 거래소에서 실제로 취소됩니다. 평소 요청 가중치는 0 이며, 상류가 고쳐지면 지워도 되는 감시라는 것까지 기록했습니다. |

## 5. 도착 호가 · 계약 정산 · 독립 대사 · 감축 · [ADR 0259](../adr/0259-arrival-book-contract-settlement-and-venue-guard-boundaries.md)

| | |
|---|---|
| **문제** | 결정 가격(종가)만으로는 실제 제출 순간의 호가 비용을 알 수 없습니다. 정산된 분기물 계약의 가상 장부와 죽은 캐시를 계속 주문 근거로 쓰면 반복 거부와 주인 없는 반대 포지션이 생깁니다. 침묵한 사용자 스트림은 체결 · 손절 발동을 놓칠 수 있습니다. |
| **결정** | 제출 순간의 실제 북 중간가를 별도 필드로 보존하고(낡으면 추정하지 않고 None), 정산 뒤에는 검증된 종료 마크로 장부를 닫습니다. 8시간 감사에서 열린 알고 주문 · 체결 내역을 캐시와 대조하되, 요청 가중치를 감사당 최대 305 · 하루 915 로 예산화하고 418/429 는 즉시 중단합니다. 발산 · 읽기 실패 종목의 감축은 무조건 `reduce_only=True` 입니다. |
| **검증** | 항목별 구현 · 검증 · 배포 창 발효를 별도 증거로 요구합니다. 결정문만으로 완료를 주장하지 않습니다. |
| **배운 점** | 운영 안전장치도 거래소 레이트 리밋 안에서 설계해야 하며, "불완전한 조회는 통과가 아니다"를 기본값으로 둡니다. |
